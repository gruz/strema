# FORPOST Stream

Трансляція відео з пристрою DZYGA на RTMP сервер з динамічним оверлеєм частоти.

## 🚀 Швидке встановлення

**Одна команда через SSH:**

```bash
curl -fsSL https://raw.githubusercontent.com/gruz/strema/master/install.sh | bash
```

Після встановлення в консолі з'явиться посилання на веб-інтерфейс:
```
🌐 Web Interface: http://192.168.1.X:8081
```

**⚠️ ВАЖЛИВО:** Стрімінг за замовчуванням **ВИМКНЕНИЙ**. Увімкніть його через веб-інтерфейс.

> **Примітка:** За замовчуванням встановлюється останній стабільний реліз.
> Якщо на пристрої стара версія бінарників `dzyga`/`dzyga_web`, інсталятор
> автоматично оновить їх до актуальної (зі збереженням бекапу).

### Перегляд у зовнішньому плеєрі

Пристрій роздає відео по RTSP на порті 8554 (посилання — у блоці превʼю
на головній сторінці):

- `rtsp://<адреса>:8554/overlay` — потік з усіма оверлеями (текст, частота)
  і інфо-плашкою над кадром (контакт, частота, стан дескремблера);
- `rtsp://<адреса>:8554/raw` — чистий потік камери без оверлею;
- `rtsp://<адреса>:8554/devvideo0` — канонічна адреса для десктопних клієнтів від розробника пристрою
  (за замовчуванням — чистий потік; перемикається на оверлейний опцією
  `RTSP_DEVVIDEO0_OVERLAY`).

RTSP — live-протокол: відставання не накопичується, бо запізнілі пакети
відкидаються, а не буферизуються. Для ще меншої затримки:

- **mpv**: `mpv --profile=low-latency rtsp://<адреса>:8554/overlay`
- **VLC**: `vlc --network-caching=300 rtsp://<адреса>:8554/overlay`
  (можна спуститись до `100`, але на поганому каналі буде розсинхрон).
- `/raw` швидший за `/overlay` на ~0.1 с — він минає енкодер зовсім.
- За замовчуванням плеєри беруть RTSP поверх UDP — найшвидший варіант.
  TCP-транспорт (проксі/VPN, що ріже UDP) додає head-of-line затримку
  при втратах.

Не відкривайте HTTP-адресу превʼю (`/api/stream/preview`) у VLC та
інших десктопних плеєрах: вона йде як «файл, що безперервно
дописується», і після кожного завмирання плеєр починає відставати
від реального часу — це відставання вже не зникає. HTTP-лінк
потрібен лише браузерному плеєру на сторінці пристрою — той сам
стежить за живим ефіром.

## 🔌 REST API і Swagger

Веб-сервіс віддає відкритий REST API на порту **8081** — без авторизації,
за IP-адресою (як і веб-інтерфейс). Масові операції флоту
(`/api/fleet/*`) додатково вимагають входу оператора.

- **Інтерактивний Swagger UI**: `http://<IP>:8081/api-docs/swagger`
  (або `/api/dzyga/ctl/docs`) — специфікація OpenAPI 3 у
  `/api/dzyga/ctl/openapi.json`. За замовчуванням показується лише
  публічний контракт; ендпоінти, які обслуговують вбудований веб-UI,
  доступні в повній специфікації `openapi.json?internal=1` з міткою
  `x-internal` (перемикач зверху сторінки Swagger UI).
- **Практичний гайд**: `http://<IP>:8081/api-docs` — рендериться з
  `web/templates/dzyga_api_docs.md`, єдиного джерела опису API
  (quickstart, приклади curl/Python, розбір SSE-екрана).
- CLI-приклад клієнта (у дереві вихідного коду):
  `python3 scripts/dzyga_api_client.py <IP> frequency 5800`.

Основні групи ендпоінтів: керування Дзигою (`/api/dzyga/ctl/*`), стрім
(`/api/stream/*`), конфіг (`/api/config*`), логи (`/api/logs*`), оновлення
(`/api/updates/*`, `/api/dzyga/*`, `/api/dzyga-web/*`, `/api/firmware/*`),
VPN (`/api/vpn/*`), мультивʼю й флот (`/api/multiview/*`, `/api/fleet/*`).

## 🛰️ Центральний хаб (опційно)

> Потребує власного VPS сервера

Пристрій може віддавати відео **один раз** на центральний сервер у VPN
(хаб), який розсилає його на RTMP-призначення і обслуговує глядачів —
для економії польового каналу. FORPOST Stream працює в двох ролях на
одному коді: **пристрій** — польовий хост з камерою (Raspberry Pi,
DZYGA); **хаб** — центральний сервер у VPN (наприклад, VPS).

```
камера → пристрій ──один RTSP──► хаб ──► RTMP-сервери (Delta тощо)
                                  └──► глядачі multiview / прев'ю / VLC
```

- Без хаба пристрій дублює потік на кожне RTMP-призначення і кожного
  віддаленого глядача — на слабкому uplink це вбиває ефір.
- Прямі пуші на RTMP-сервери **припарковані**, доки хаб живий (у таблиці
  цілей — стан «Через хаб»); якщо хаб недоступний >15 с — пристрій
  автоматично повертається на прямі пуші, а коли хаб стабільний >10 с —
  знову на хаб.
- Віддалені глядачі (Tailscale/ZeroTier/WireGuard/інтернет) дивляться
  **через хаб** — пристрій віддає їм нуль байтів окремо; лише глядач у
  справжній LAN пристрою дивиться напряму.

### Вимоги до сервера хаба

- x86-64 Linux (Debian/Ubuntu), ~2 vCPU / 4 GB RAM орієнтовно на ~20
  пристроїв (без перекодування — лише копіювання потоків);
- `ffmpeg` і `mediamtx` ставляться інсталятором;
- сервер у тому ж VPN, що й пристрої;
- відкритий порт **8554/tcp** для RTSP-публікацій (на WAN-адресі, якщо
  хаб має публічний IP); веб **8081** навмисно НЕ відкритий у WAN —
  файрвол юніта `forpost-hub-webfw` + вбудований гвард пропускають
  лише loopback, локальну мережу і VPN-пірів;
- VPN-мережі для реєстрації пристроїв і глядачів визначаються
  автоматично (Tailscale-піри, підмережі тунельних інтерфейсів
  WireGuard/OpenVPN/ZeroTier) — додаткового конфігу не потрібно;
- медіа-ендпоінт хаб визначає сам: публічна WAN-адреса, коли вона є
  (стрім іде напряму, без VPN-капсули), інакше VPN-адреса — нуль
  конфігу в обох випадках.

### Встановлення хаба

```bash
# одним рядком (curl-інсталятор у ролі хаба)
curl -fsSL https://raw.githubusercontent.com/gruz/strema/master/install.sh | STREMA_ROLE=hub bash

# або з локальної копії репо
STREMA_ROLE=hub sudo ./install.sh
```

Після встановлення роль зберігається маркером `config/hub.enabled` —
наступні оновлення тим же інсталятором залишають хаб-режим.

Веб-інтерфейс хаба: `http://<hub>:8081` — доступний лише через VPN
або локальну мережу хаба (з публічного інтернету порт закритий),
відкривається одразу мультив'ю, у шапці бейдж **ХАБ**, сторінка
«Обслуговування» без камера/DZYGA-контролів. Роль визначається
автоматично.

### Налаштування пристрою

1. Відкрийте веб пристрою → розділ **«Сервери трансляції (RTMP)»**.
2. Рядок **«Хаб»**: перемикач **Так** + **VPN-адреса** хаба, напр.
   `100.123.45.67` (можна `host:port` — порт = веб-API хаба, 8081).
   Це єдина адреса, яку пристрій зберігає: при реєстрації хаб повертає
   медіа-ендпоінт (авто-визначений), куди йде стрім.
3. Збережіть конфігурацію — стрім перезапуститься.

Пристрій публікує потік як `rtsp://<hub>:8554/<device_id>`
(`device_id` — серійник або стабільний hardware id; видно в
`/api/device/info` і в адресі публікації на хабі).

### Як це виглядає для глядачів

- **Мультив'ю** (`http://<hub>:8081/multiview`): комірки пристроїв із
  ввімкненим хабом беруть прев'ю з хаба — rate-бейдж `H`, тултіп
  «стрім через центральний хаб».
- **Сторінка пристрою**: віддалений глядач (не LAN) отримує прев'ю з
  хаба; LAN-глядач — локальне прев'ю пристрою. У блоці «Відео»
  з'являється рядок «Через хаб — основний стрім» (RTSP) — основна
  адреса для перегляду; прямі лінки пристрою ховаються під спойлер
  з попередженням, що кожен глядач за ними тягне окрему копію стріму
  через VPN (локальна мережа/fallback).
- **«Стріминг і глядачі»** на пристрої: глядачі через хаб видно
  окремо — рядки з бейджем `хаб` (IP/браузер/шлях) + підсумок
  «Глядачі через хаб: N»; локальні — як раніше.
- **VLC/RTSP**: `rtsp://<hub>:8554/<device_id>` — той самий стрім,
  що пристрій публікує на хаб (з оверлеєм); у меню лінків мультив'ю
  і на сторінці пристрою він іде першим, прямі лінки — з позначкою
  «— напряму».

### Експлуатація

Сервіси на хабі (ті самі unit-імена, що на пристрої):

- `forpost-mediamtx` — медіасервер, прийом потоків пристроїв;
- `forpost-hub-relay` — бере targets, які пристрої push'ать при
  реєстрації перед publish, і піднімає незалежні `ffmpeg -c copy` job
  на кожну RTMP-ціль;
- `forpost-stream-web` — веб (мультив'ю, прев'ю, API).

```bash
systemctl status forpost-hub-relay forpost-mediamtx
journalctl -u forpost-hub-relay -f   # лог relay-хаба
curl http://<hub>:8081/api/hub/viewers   # хто зараз дивиться через хаб
```

Налаштування relay — ключі `HUB_*` (API mediamtx, RTSP-порт,
інтервали полінгу, ліміти, VPN-підмережі) — зібрані в
`config/hub_defaults.conf`; значення за замовчуванням збігаються з
вбудованими, тож міняти їх треба лише при нестандартній розкладці
хаба. Relay читає конфігурацію один раз при старті — після зміни
перезапустіть `forpost-hub-relay`.

Сторінка **«Канали хаба»** (`/hub`, пункт у меню) — по картці на
кожен пристрій, що публікує на хаб. Заголовок картки — статичний
текст оверлею пристрою (`OVERLAY_TEXT`, той самий «людський» напис,
що на відео); якщо він не заданий — показується `device_id`, а за
наявності тексту ID лишається дрібним поруч:

- **Вхід**: `⇑` — publish-сесія mediamtx: IP пристрою, транспорт
  (UDP/TCP), швидкість прийому і тривалість з'єднання.
- **Канали на сервери**: relay-job на кожну RTMP-ціль — стан
  (`up`/`connecting`/`down`), швидкість, RTT, аптайм, лічильник
  перезапусків і час до наступної спроби. Дані — знімок
  `/tmp/strema_hub_relay.json`, який relay переписує кожні ~2 с;
  застарілий файл означає, що сервіс лежить.
- **Читають з хаба**: ті самі колонки, що «Стріминг і глядачі» на
  сторінці пристрою — хто (ім'я хоста + бейдж мережі TS/LAN/WAN +
  IP), чим (RTSP / «Браузер · multiview» / плеєр + бейджі
  браузера й ОС), тривалість і трафік. Джерела: зовнішні
  RTSP-сесії mediamtx (VLC тощо) і HTTP-прев'ю клієнти
  (`/api/hub/preview`). Loopback-читачі (relay- і прев'ю-ffmpeg) не
  перелічуються — вони вже відображені в каналах.

Усе разом віддає `GET /api/hub/streams`; сесійна частина живе в
mediamtx API (`HUB_MEDIAMTX_API`, типово `127.0.0.1:9999`) — коли він
недоступний, сторінка показує `sessions_ok=false` і працює лише за
relay-знімком.

Оновлення хаба — тим же `install.sh` (маркер `hub.enabled` збереже
роль). На пристроях оновлення не торкаються хаба.

### Обмеження

- Один стрім на пристрій: проксі-нога копіює **головний** потік
  (оверлей за `STREAM_MODE`); `raw`-нога на хаб не публікується.
- `overlay`-режим рекомендований; `raw` — відкритий дизайн-питання.
- Глядачі через хаб видно на `/hub` (по пристроях) і в статистиці
  пристрою — в обох випадках окремо від локальних читачів.
- Якщо хаб лежить — прев'ю віддалених глядачів недоступне (прямі
  RTMP-пуші при цьому failover'яться на пристрої самі).
